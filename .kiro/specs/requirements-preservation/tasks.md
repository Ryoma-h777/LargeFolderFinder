## Implementation Notes

- 抽出元は Git 管理外の唯一の写しである。読み取り専用として扱い、作業中に一切変更しないこと
- 抽出の根拠は記録本体に限る。編集履歴のスナップショットはフォルダ横断で同一の連番チェーンであり固有の情報を持たず、付随するメタデータの要約は内容と食い違う例が実測で複数見つかっている
- 保全先本体は全文が常時読み込まれる。分量の目安（200行）を超えないこと。分量の大きい索引はスペック配下に置く。設計の見込み（250〜400行）は3つの成果物の合計であり、保全先本体単体の上限ではない
- 保全するのは値ではなく理由である。抽出元の設定値は当時値であり、現行コードと食い違う箇所がある
- 旧AIモデルの生成物であるため、記述を鵜呑みにしないこと。コードで裏を取り、取れないものは取れないと明示すること
- 持ち込んではならない文字列の一覧（タスク1.2）は機密そのものを含む。バージョン管理の対象に置かないこと
- **作業開始時点のハッシュ一覧は、セッションのスクラッチパッド配下 `rp-work/baseline/` に読み取り専用で置いた**（タスク1.1、2026-09-16）。抽出元は539ファイル・42フォルダ（うち `.md` 108、空フォルダ4）。照合手順は同じディレクトリの `snapshot.sh`。**タスク4.1では出力先を必ず別のディレクトリに指定すること**。省略するとスクリプトと同じ場所に書き出し、新しい一覧を自分自身と比べて照合が必ず「一致」になる（レビューで指摘）。スクラッチパッドはセッション専用のため、4.1を別のセッションで行う場合は一覧が残っているかを先に確かめること
- **持ち込み禁止の確認は `rp-work/check-forbidden.sh` で行う**（タスク1.2、2026-09-16）。パターン20件と、パターンごとの見本20行（どちらも機密そのものを含むためリポジトリの外）。使い方と終了コードは同じディレクトリの `forbidden-patterns.md`。**「機密なし」と言えるのは終了コード0だけ**。2は「確認できなかった」であり、合格ではない
- **引数は、パスを明示した通常のファイルだけを受け付ける。ディレクトリは受け付けない**。ディレクトリ配下を調べるときは呼び出し側でファイル一覧に展開し、その件数を独立した基準と照合してから渡すこと（`docs/` の `.md` は基準一覧で108件、steering は `find .kiro/steering -type f` の件数）。照合を省くと、展開の漏れを誰も検出できない
- **確認用スクリプトは、レビューで4回差し戻され、2回のデバッグを経て作り直した**。4回とも「確認が成り立っていないのに終了コード0を返す」同じ種類の欠陥だった（存在しないパス、壊れた正規表現、UTF-16 や NUL を含むファイル、パターンファイルの BOM、`-` で始まるディレクトリ、パターンと見本が共有する行末の空白）。1回目のデバッグは「確認不能な状況を1つずつ弾く拒否リスト方式では終わらない」と結論し、2を既定として証明がそろったときだけ0/1を返す作りに改めた。2回目のデバッグは「受け付ける入力の範囲が実際の使い道より広すぎる」と結論し、入力をパスを明示したファイルに絞り、パターンと見本の書式を厳しく決め、「渡したものをすべて読んだ」ことを証明に加えた。**確認の仕組みを作るときは、使い道に合わせて入力の範囲を先に絞ること。便利さのために受け付ける形を増やすと、同じ種類の穴が戻る**
- 見本による証明は「パターンが書いたとおりに働く」ことしか示さない。パターンが捕まえるべき形を取り漏らしていないか（全角英字で書かれた利用者名など）は、人が判断するしかない
- 保全先に既定のタブの初期値（ドライブ直下）を書くときは、パスの形ではなく「C ドライブ直下」のように文章で書くこと。パスの形で書くとドライブ文字のパターンに当たる
- **このスペックの作業中に、scan-golden-baseline の文書とコードのコメントに利用者名の短縮形が混入していたことが見つかり、伏せ字に直した**（13c39a4）。混入を含む過去のコミット（7e1d296、43db257）は未 push のブランチの履歴に残っている。扱いはユーザーの判断待ち
- **保全しないと確定したのは8フォルダ**（タスク2.1）: 空4、作業ログ・ビルド修正3、コードの事実の再掲1（管理者再起動のツールチップの訳文のみ）。残る34フォルダは、中身に抽出対象を含むと判断してタスク2.2に委ねた。フォルダ名と中身が違う例（`fix_scan_completion_display` の中身はフォルダ選択ダイアログの修正で、利用者の要望によるログ追加を含む）があるので、2.2でも中身で分類すること
