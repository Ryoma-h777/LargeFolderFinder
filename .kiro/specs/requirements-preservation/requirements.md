# Requirements Document

## Project Description (Input)
`docs/` 配下42フォルダ（108ファイル・約3,100行）の旧AIモデル生成ドキュメントから、利用者の要望・仕様上の決定とその理由・却下された案・明示的な非目標を抽出し、`.kiro/steering/` 配下へ保全する。

**誰の問題か**: Large Folder Finder の開発者（個人開発、単独）。大幅なリファクタリングにあたり「私の要望だけは残しつつ」という明確な要求がある。

**現状**: 要望の記録は旧AIモデル（Gemini 2.0/2.5世代）が生成した設計ドキュメントとして `docs/` 配下に散在し、`.gitignore` の `/docs/` により Git 管理外に置かれている。バックアップもなく、**このマシン上の1つの写ししか存在しない**。失われれば、何のためにその実装がその形になっているのかを復元する手段がなくなる。`.kiro/steering/` の4本（product / tech / structure / performance）はいずれも現状のコードから読み取れる事実を記述したもので、「なぜそうしたか」の要望レベルの経緯を含まない。

**何が変わるべきか**: 要望・仕様上の決定・その理由が `.kiro/steering/` へ抽出され、Git 管理下で保全される。リファクタリング中に「この挙動は変えてよいのか」を判断する根拠が参照できる。

**制約**: `docs/` は読み取り専用として扱い、Git 管理外のままとする（開発者の判断）。全文転記はせず、steering の粒度方針（パターンと理由を残し、網羅的な列挙は避ける）に従う。抽出元と抽出先の対応関係を記録して後から辿れるようにする。旧AIモデルの生成物であるため記述がコードと食い違う可能性があり、コードで確認できた事実とドキュメントにしかない意図を区別して記録する。食い違いは記録にとどめ、修正は後続スペックに委ねる。コードの変更は行わない。

詳細な背景・境界・制約は [brief.md](brief.md) を参照。

## 前提と留意点（棚卸しの実測、2026-09-16）

- `docs/` は42フォルダ・539ファイル。**うち431ファイルは `*.resolved*` と `*.metadata.json`** で、旧AIツールの編集履歴のスナップショットである。フォルダ横断で同一の連番チェーンになっており、フォルダ固有の情報を持たない
- `.metadata.json` の `summary` は内容と食い違う例が複数ある（フォルダの内容と無関係な要約、実装と逆の要約）。根拠に用いない
- フォルダ名と内容が一致しない例がある（`fix_scan_completion_display` の中身はフォルダ選択ダイアログの修正）
- 4フォルダは空、7フォルダは純粋なビルドエラー修正や作業ログで保全価値が薄い
- `.md` 108ファイルのうち**34ファイルに、Windows のユーザー名を含む絶対パスが `file:///` 形式で含まれる**。ほかに個人のアカウント名を含むURLが1箇所
- `docs/` の設定値は**当時値**であり、現行コードおよび `.kiro/steering/performance.md` と食い違う箇所がある（事前カウントの階層数、平滑化の係数）
- 抽出後の分量は250〜400行程度の見込み（入力3,132行に対し圧縮率およそ90%）
- `.kiro/steering/roadmap.md` は「41フォルダ」と記述しているが実際は42フォルダである

## Introduction

本フィーチャーは、旧AIモデルとの開発のやり取りが残る `docs/` 配下のドキュメントから、**利用者の要望・仕様上の決定とその理由・却下された案・明示的な非目標**を抽出し、Git 管理下の `.kiro/steering/` へ保全するものである。

守る対象は「なぜその実装がその形になっているか」という**意図**である。現状のコードから読み取れる事実は既存の steering が記述しているが、意図の記録は `docs/` にしか存在せず、そのフォルダは Git 管理外でバックアップもない。

本フィーチャーはドキュメント作業に徹し、コードを一切変更しない。抽出した意図と現在のコードが食い違っていた場合も、記録するにとどめ、修正は後続のスペックに委ねる。

## Boundary Context

- **In scope**: `docs/` 配下の棚卸しと分類、要望・決定・理由・却下案・非目標の抽出、`.kiro/steering/` への保全、既存 steering との重複排除と整合、抽出元と抽出先の対応関係の記録、機密情報の除去
- **Out of scope**: `docs/` 自体を Git 管理下へ移すこと（開発者の判断で管理外のまま）、ドキュメントの全文転記、コードの変更、抽出した意図と現在のコードの食い違いの修正
- **Adjacent expectations**: 後続の全スペックが本フィーチャーの成果を「この挙動は仕様か不具合か」の判断根拠として参照する。とくに `scan-correctness` と `ui-redesign` はこの判断に依存する。`dotnet10-migration` は、1回目の実行基盤の移行が品質面で失敗した記録を参照する

## Requirements

### Requirement 1: 棚卸しの網羅性と対象の確定

**Objective:** As a 開発者, I want `docs/` のすべてのフォルダについて扱いが決まっていること, so that 保全漏れがないと確信できる

#### Acceptance Criteria

1. The 保全作業 shall `docs/` 配下のすべてのフォルダについて、「抽出した」「読んだが保全しない」のいずれかの扱いを記録する
2. The 保全作業 shall 抽出の根拠を `docs/` 配下の `.md` ファイルに限定する
3. The 保全作業 shall 編集履歴のスナップショット（`*.resolved*`）および付随するメタデータ（`*.metadata.json`）を抽出の根拠に用いない
4. The 保全作業 shall メタデータに含まれる要約を、内容の判断根拠に用いない
5. If フォルダ名と内容が一致しないとき, then the 保全作業 shall 内容を根拠として分類する
6. When フォルダが空であるとき, the 保全作業 shall その事実を記録し、保全の対象外とする
7. If フォルダの内容が一度きりの作業ログまたはビルド環境の修正のみであるとき, then the 保全作業 shall 保全しない理由とともにその判断を記録する

### Requirement 2: 抽出する内容

**Objective:** As a 開発者, I want 要望・決定・理由・却下案・非目標が残ること, so that リファクタリング中に「この挙動は変えてよいのか」を判断できる

#### Acceptance Criteria

1. The 保全作業 shall 利用者から出た要望を、要望として識別できる形で記録する
2. The 保全作業 shall 仕様上の決定について、決定の内容とその背景にある理由を対にして記録する
3. The 保全作業 shall 試して却下された案について、何を試し、なぜ捨てたかを記録する
4. Where 却下された案を再び提案してはならない条件が読み取れるとき, the 保全作業 shall その条件を記録する
5. The 保全作業 shall 明示的な非目標（やらないと決めたこと）を記録する
6. The 保全作業 shall 網羅的な列挙を避け、パターンと理由を残す
7. The 保全作業 shall 現在のコードから読み取れる事実の再掲を避ける

### Requirement 3: 事実と意図の区別、および食い違いの扱い

**Objective:** As a 開発者, I want 裏の取れた事実と、記録にしかない意図が見分けられること, so that 旧AIモデルの記述を鵜呑みにせずに済む

#### Acceptance Criteria

1. The 保全作業 shall コードで確認できた事実と、ドキュメントにしか書かれていない意図とを、読んで区別できる形で記録する
2. While ドキュメントの記述と現行のコードが食い違っている間, the 保全作業 shall 現行のコードを正とし、ドキュメントからは理由のみを採る
3. If ドキュメントの記述と現行のコードの食い違いを見つけたとき, then the 保全作業 shall その食い違いを記録し、コードを修正しない
4. The 保全作業 shall 食い違いの扱いを後続のスペックに委ねる旨を、記録とともに残す
5. If ドキュメント内で記述どうしが矛盾しているとき, then the 保全作業 shall 矛盾していることを含めて記録する

### Requirement 4: 機密情報の除去

**Objective:** As a 開発者, I want 保全先に個人情報や環境固有の情報が残らないこと, so that リポジトリを公開したままにできる

#### Acceptance Criteria

1. When 抽出元にローカルの絶対パスが含まれるとき, the 保全作業 shall パスの所在を示す部分を除去し、必要であればファイル名のみを残す
2. The 保全作業 shall Windows のユーザー名を保全先に持ち込まない
3. The 保全作業 shall 個人のアカウント名を含む URL を保全先に持ち込まない
4. The 保全作業 shall 旧開発ツール由来の内部マーカーを保全先に持ち込まない
5. The 保全作業 shall 保全先に上記が含まれていないことを、機械的に確認できる形で示す

### Requirement 5: 抽出元への追跡可能性

**Objective:** As a 開発者, I want 保全した記述の出どころを辿れること, so that 疑問が生じたときに原典を確認できる

#### Acceptance Criteria

1. The 保全作業 shall 保全した各記述について、抽出元のフォルダとファイルを辿れる形で記録する
2. The 保全作業 shall 抽出元と抽出先の対応関係を一覧できる形で残す
3. While `docs/` が Git 管理外である間, the 保全作業 shall 抽出元が失われた場合に何が参照できなくなるかが分かる形で記録を残す

### Requirement 6: 既存の記録との整合

**Objective:** As a 開発者, I want 保全先が既存の steering と矛盾せず重複もないこと, so that どれを読めばよいか迷わない

#### Acceptance Criteria

1. If 抽出した内容が既存の steering に既に書かれているとき, then the 保全作業 shall 同じ内容を重ねて書かない
2. Where 既存の steering に理由が欠けている決定があるとき, the 保全作業 shall 既存の記述に理由を補う
3. The 保全作業 shall 保全先の1ファイルを単一のトピックに絞り、分量の目安を超えないようにする
4. If 既存の記録に事実と異なる記述を見つけたとき, then the 保全作業 shall その記述を訂正する
5. The 保全作業 shall 保全先が常時読み込まれるか、必要なときだけ読み込まれるかを、内容の性質に応じて定める

### Requirement 7: 作業の安全性

**Objective:** As a 開発者, I want 唯一の写しである `docs/` が作業で失われないこと, so that 安心して作業を任せられる

#### Acceptance Criteria

1. The 保全作業 shall `docs/` を読み取り専用として扱う
2. The 保全作業 shall `docs/` 配下のファイルおよびフォルダを、変更・削除・移動しない
3. The 保全作業 shall `docs/` を Git 管理外のままとする
4. The 保全作業 shall アプリケーションおよび検証ツールのコードを変更しない
5. When 保全が完了したとき, the 保全作業 shall `docs/` が作業前と同一であることを確認できる形で示す
