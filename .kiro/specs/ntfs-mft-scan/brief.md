# Brief: ntfs-mft-scan

## Problem

利用者の判断（2026-09-22）により、このアプリの存在意義のため **WizTree と同等以上の走査速度** を目標とした。

WizTree が非常に速いのは、ローカルの NTFS ドライブを管理者として走査するとき、ディスクの MFT（Master File Table: 全ファイルの名前・大きさ・親子関係の目録）を直接読むためである。ファイルやフォルダを1つずつ開いて列挙する通常の方法では、どれだけ並列化を作り込んでもこの場面では追いつけない（[diskanalyzer.com](https://diskanalyzer.com/)、[FolderSizes の比較](https://www.foldersizes.com/features/wiztree)）。

一方、NAS・NTFS 以外・管理者でない場合は WizTree も通常の列挙に戻る。そちらの場面は `scan-performance` が並列化で上回ることを目指す。本スペックは **ローカルの NTFS を管理者として走査する場面** を受け持つ。

## Current State

- 走査は通常の列挙（`DirectoryInfo.EnumerateFiles` / `EnumerateDirectories`）のみ
- 「管理者として開き直す」メニューは既にある（decisions.md）
- 集計値の正しさは `scan-golden-baseline` の期待値データとの比較で確かめられる。検証用のフィクスチャは `%TEMP%`（通常はローカルの NTFS の C ドライブ）に作られるため、MFT の読み取りの結果とも比較できる

## Desired Outcome

- ローカルの NTFS ドライブを管理者として走査するとき、MFT を直接読む走査方式が使われ、**WizTree の最速モードと同等以上の所要時間**になる
- 使えない条件（NAS、NTFS 以外、管理者でない、読み取りに失敗した）では、自動的に通常の走査に戻る。利用者はどちらで走査したかが分かる
- 走査の対象がドライブ全体でなくフォルダでも、そのフォルダの配下だけを結果にする
- 集計値が通常の走査と一致する（下記の違いが出うる点は、扱いを決めて記録する）
- 所要時間が WizTree と並べて実測され、performance.md に記録されている

## Approach

設計の前に**技術的な調査（spike）**を行い、方式を決める。候補は次の2つ。

1. **MFT のレコードを生で読んで解析する**（WizTree の方式）。ボリュームのハンドルを開き、`FSCTL_GET_NTFS_VOLUME_DATA` で MFT の位置を得て、ファイルレコードを連続で読み、`$FILE_NAME`・`$STANDARD_INFORMATION`・`$DATA`（実サイズ・割り当てサイズ）・属性リストを解析する。大きさまで一度に得られるので最速だが、解析の実装量が多い
2. **`FSCTL_ENUM_USN_DATA` で目録を列挙する**（Everything の方式）。名前と親子関係は速く得られるが、大きさが含まれないため、大きさは別途取り直す必要があり、目標の速度に届かない可能性が高い

どちらも OS の呼び出し（`CreateFile` でボリュームを開く、`DeviceIoControl`、`ReadFile`）が要る。**プロジェクトは P/Invoke の除去を進めているが、これは長いパスの制約を避けるためであり、ボリュームのハンドル（`\\.\C:`）はパスを渡さないので長いパスの問題は生じない**。例外として認め、この部品に閉じ込める。

## Scope

- **In**:
  - 方式の技術調査と、所要時間の実測による選定
  - MFT の直接読み取りによる走査（ローカルの NTFS、管理者のとき）
  - 対象がフォルダのときの配下の絞り込み
  - 使えない条件の判定と、通常の走査への自動の切り替え
  - どちらの方式で走査したかの記録と表示（表示の見せ方は最小限。整えるのは `ui-redesign`）
  - 期待値データとの比較（物理サイズ換算の有無の両方）と、WizTree との比較の実測
- **Out**:
  - 通常の列挙の経路の高速化（`scan-performance`）
  - 常駐して変更を監視する仕組み、インデックスの事前構築
  - NTFS 以外のファイルシステム（ReFS・FAT・exFAT）の目録の直接読み取り

## Boundary Candidates

- ボリュームの判定（NTFS か、ローカルか、管理者か）
- MFT の読み取りと解析
- 親子関係からのツリーの組み立てと、対象フォルダの配下への絞り込み
- 通常の走査への切り替え

## Out of Boundary

- 結果のツリーの型の設計（`scan-performance` が決めたものに合わせる）
- 画面の新しい表示の設計（`ui-redesign`）

## Upstream / Downstream

- **Upstream**: `scan-performance`（結果のツリーの構造と走査の入口が確定していること）、`scan-correctness`（失敗の扱いの方針）、`scan-golden-baseline`（集計値の比較）
- **Downstream**: `architecture-refactoring`（走査の方式の選択を含む画面との接続を整理する）

## Constraints

- **集計値が通常の走査と一致すること。** ただし MFT を直接読むと、通常の列挙と結果が変わりうる点がある。**それぞれの扱いを設計で決め、決定を記録する**
  - **アクセス権の無いフォルダ**: MFT の読み取りはフォルダのアクセス権を経由しないため、通常の走査ではスキップされるフォルダの中身の大きさも数えられる。WizTree はこれを数える。**数えるか、通常の走査に合わせて除くかは利用者の判断が必要**（容量の調査の目的には数えるほうが有用だが、見えない場所の大きさが出ることになる）
  - **ハードリンク**: 1つのファイルに複数の名前がある。通常の列挙は名前ごとに数える。同じに扱うか、1回だけ数えるか
  - **代替データストリーム**、**圧縮・スパースのファイル**の大きさ（論理サイズと物理サイズ）
  - システムのメタデータ（`$MFT` など）や、ごみ箱・シャドウコピーの扱い
- 管理者権限が必要。昇格していないときは黙って遅い方式にせず、どちらで走査したかが分かるようにする
- 対象がフォルダでも MFT はボリューム全体を読むことになる。小さなフォルダの走査では通常の走査のほうが速い場合がある。切り替えの基準を実測で決める
- ボリュームの生の読み取りは、ドライブ全体のファイル名などのメタデータに触れる。読み取るだけで書き込まないこと、得た情報を走査の結果以外に残さないこと
- 新しいパッケージは原則として追加しない。追加する場合は無料で商用利用可能なこと（roadmap の「ライセンス」）
- WizTree との比較は利用者の PC に WizTree を入れて行い、配布物には同梱しない
