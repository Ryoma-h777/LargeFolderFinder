## Implementation Notes

- 自己検証の項目は1つのファイルにまとめて登録するため、2.1〜2.4 は並行させず順に進める
- 4.1 と 4.2 は同じ言語ファイルを触るため並行させない
- アプリ本体はビルドしない。ツールはアプリを再ビルドしない指定でビルドする（アプリのビルド出力は既存のものを使う）
- 検証ツールはキー一覧をアプリのビルド出力から得る。ビルド出力が古いと、キーの数を誤ったまま「問題なし」と出る
- 終了コードの定数は 1.2 で private に戻した（タスク1.1のレビューの指摘）
- 自己検証で予期しない例外が出たときは、理由に例外の型名を添えると原因を追いやすい（タスク1.2のレビュー）
- 2.4 の完了時点で「登録された項目の数が想定以上であること」自体を1項目にすると、登録が消えても気づける（タスク1.2のレビュー）
- 差し込み位置の取り出しは、設計の規則（`{番号}`・`{番号,幅}`・`{番号:書式}`・`{番号,幅:書式}`）に忠実にした。`.NET` が実際には許す空白入り（`{0 }`）や書式内のエスケープは認識しない。実データには無く、認識しない側に倒すと見落としではなく過剰報告になる（タスク2.1のレビュー）
- `ParseIndexes` は null で例外を投げる契約。2.3 で呼ぶときに自己検証の項目を1つ足す（タスク2.1のレビュー）
- **設計の誤りを実装で見つけた**（タスク2.2）: 重複キーを表現モデル（`YamlStream`）で数える案は、`YamlStream.Load` が重複キーで例外になるため成立しない。解析器の事象の列で数える形に改め、`design.md` と `research.md` を実測に合わせて直した
- **自己検証は変異を入れて確かめる**（タスク2.2のレビュー）: 値の読み飛ばしの行を外しても全項目が通っていた。実データでは12言語で誤検出になる壊れ方だった。分岐ごとに、壊すと落ちる項目があるかを確かめること
- 読み込み不能なファイルでも重複キーの一覧は返る。報告に出さないのは 2.3 の役目（例: `A: [1, 2]` と `A: [3]` は読み込み不能かつ重複あり）
- 自己検証の入力に1文字のキーと改行を並べると（`"A:" + 改行`）、持ち込み禁止の検査でドライブ文字から始まる絶対パスとして誤検出される。テスト用のキー名は2文字以上にすること（タスク2.2）
