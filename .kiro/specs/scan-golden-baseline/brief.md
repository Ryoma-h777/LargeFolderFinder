# Brief: scan-golden-baseline

## Problem

Large Folder Finder には**自動テストが1つも存在しない**。全5,213行のコードベースに対して大規模なリファクタリングと .NET 10 移行を行うが、変更によって走査結果の数値が変わっても誰も気づけない。

このアプリの提供価値は「どのフォルダが何バイトか」を正しく示すことにある。速度改善のために `FolderInfo.AddSize` の集計方式を作り替え、列挙方式を `FileSystemEnumerator<T>` へ置き換える計画があるため、**集計ロジックそのものが書き換わる**。安全網なしでこれを行うのは危険度が高い。

## Current State

- テストプロジェクトなし、CI なし
- 検証は実機での手動確認と、README に載せる実測タイムのみ
- 走査結果を外部に書き出す手段は「クリップボードへのコピー」だけで、表示条件（フィルタ・折りたたみ・単位）の影響を受けるため期待値として使いにくい

## Desired Outcome

- 既知のフォルダ構造に対する走査結果が、**パスとサイズの一覧**として安定した形式で記録されている
- 変更前後の結果を比較し、差分を検出できる
- この期待値データが **.NET Framework 4.8 から .NET 10 への移行をまたいで使える**

## Approach

テストコードではなく**データを先に作る**。現行の v1.0.3 で既知フォルダを走査し、正規化した一覧を出力して期待値として保存する。移行後に .NET 10 上でテストプロジェクトを作り、このデータと突き合わせる。

期待値データを .NET のバージョンやシリアライズ形式に依存させないことが要点である。素朴なテキスト形式（1行1エントリ、パスとサイズと種別）とし、並列走査による順序の揺れを排除するためソートを固定する。

検証用のフォルダ構造は、少なくとも以下を含むこと。
- 深い階層（後続の長いパス対応の検証にも使えるよう260文字超を含む）
- 日本語を含むパス
- 空フォルダ、サイズ0のファイル
- アクセス権のないフォルダ（走査が継続することの確認）

## Scope

- **In**:
  - 期待値データの形式定義（移行をまたいで使える素朴なテキスト形式）
  - 現行 v1.0.3 から期待値を生成する手段
  - 期待値と実行結果を比較し差分を報告する仕組み
  - 検証用フォルダ構造の定義と生成手順
  - 物理サイズ（クラスタアライメント）の有無による結果差の扱いの明確化

- **Out**:
  - .NET 10 上でのテストプロジェクト本体の構築（`dotnet10-migration` 以降で行う）
  - 速度の計測と回帰判定（performance.md の手順に従い、別途実測で行う）
  - UI の表示結果の検証

## Boundary Candidates

- 期待値データの形式定義と生成
- 比較・差分報告
- 検証用フォルダ構造の準備

## Out of Boundary

- 走査ロジックそのものの変更（このスペックは現行の挙動を「記録する」ことに徹し、正しさの判断はしない。長いパスの欠落など既知のバグも、現時点の挙動として記録する）
- テストフレームワークの選定と導入（`dotnet10-migration` で xUnit v3 を導入する）

## Upstream / Downstream

- **Upstream**: なし（最初に着手できる）
- **Downstream**: `dotnet10-migration`、`scan-correctness`、`scan-performance` がこの期待値データに依存する

## Existing Spec Touchpoints

- **Extends**: なし（既存スペックなし）
- **Adjacent**: なし

## Constraints

- 期待値データは **.NET のバージョン・シリアライズ形式・クラス構造に依存しない**こと。移行をまたいで使えることが本スペックの存在意義である
- 並列走査のため列挙順序は不定。ソートを固定して比較可能にすること
- 現時点の挙動には既知のバグが含まれる（260文字超のパスが集計から漏れる）。**バグを含んだ状態が期待値になる**ため、`scan-correctness` で修正した際は期待値の更新が必要になる。どのエントリが既知バグ由来かを記録に残すこと
- steering の performance.md に記載した計測手順と矛盾しないこと
