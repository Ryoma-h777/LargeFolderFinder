  - 観測可能な完了状態: 期待値データを表す型が定義され、更新日時と所有者を保持する手段が型として存在しない

## Implementation Notes

- テストフレームワークの導入は本スペックの対象外（`dotnet10-migration` の範囲）だが、テスト先行で実装を進める土台が必要なため、外部依存を持たない自己検証ハーネスをタスク1.1の土台に含めることとした。承認済みの範囲境界（外部のテストフレームワークを導入しない）は維持している。タスク6.1・6.2 はこのハーネスに具体的な検証項目を積む形で実装し、移行後に xUnit v3 へ引き上げる
- 本体は SDK 形式 csproj の glob でリポジトリ配下の全 `.cs` を収集する。新規プロジェクトを追加する際は `DefaultItemExcludes` への追記が必須。追記前は本体ビルドが `CS0017 複数のエントリポイント` で失敗する（タスク1.1 で実測）
- `.gitignore` に `/fixtures/`（生成されるフィクスチャの実体の置き場）を追加済み。design.md には明記のない規約なので、タスク3.x でフィクスチャの実配置先を確定する際に整合を再確認すること
- Model 層の不変条件（サイズが0以上、基準の論理名が空でない等）は構築時例外として実装済みだが、異常系を証明する自己検証項目がまだ無い（タスク1.2 のレビュー指摘）。後続の検証タスク 6.1 で異常系の項目を追加すること
- 拡張長パス（`\\?\`）の取り扱いは `Tools/GoldenBaseline/Io/LongPath.cs` に閉じている。**フィクスチャの生成・削除を含め、長いパスを触る箇所は必ず `LongPath.Extend` を経由すること。** プレーンなパスは260文字を超えると Win32 が拒否する（`DirectoryNotFoundException`）
- ディレクトリの文字数境界は248、ファイルパスは260。数え方は文字数でバイト数ではない（タスク3.3 のフィクスチャ設計で両方の境界をまたぐこと）
- 期待値ファイルの形式（タスク2.1で確定）: ヘッダは `# キー: 値`、キー名は `GoldenHeader` のプロパティ名に対応。`FixtureOmissions` は `# FixtureOmission: ...` を項目ごとに複数行で表現。形式バージョンの初版は `1`。真偽値は `true`/`false` 小文字固定。日時は往復可能な `"o"` 形式。読み書きの失敗は専用例外 `GoldenFormatException` で通知
- **検証項目は「壊したら失敗するか」を必ず変異テストで確かめること。** タスク2.1では並び順の検証データが偶然 Ordinal と既定比較で同じ並びになり、`StringComparer.Ordinal` を差し替えても23件全てが通過していた（レビューで差し戻し）。期待値は文字列リテラルで明示し、比較規則の違いが必ず現れるデータ（`co-op` / `coop` / `cop` など）を選ぶこと
- 差分の判定で「設定不一致のときに突き合わせを行わない」ことは、判定値だけを見ても検証できない。**`Entries` が空であることまで照合する必要がある**（タスク2.2 のレビューで、内部で突き合わせつつ判定値だけ差し替える変異を試して確認済み）。同種の「短絡することが仕様」の検証では常にこの観点を入れること
- フィクスチャ定義（タスク3.1で確定）: `FixtureSpec.Standard` が21項目。長いパスは5階層×50文字の連鎖で最深フォルダ254文字（>248）、その配下のファイルが ASCII 272文字・日本語 265文字（>260）。ファイルサイズは 10 / 4096 / 4097 バイトを混在させ、クラスタ境界（4096を仮定）の跨ぎ有無で物理サイズ換算の丸めが確認できるようにしている
- **Trait のラベルと実体は分けて検証すること。** `LongPath` が付いていても実際の文字数が足りない、`Japanese` が付いていても実際は ASCII、という形骸化が起きる。タスク3.1では文字数と非ASCII文字の実測で照合している
- **ACL を扱う検証で `RestoreRead` を壊す変異を行うと、削除できないフォルダが実際に残留する。** タスク3.2の実装時に4件残留し、`icacls <path> /reset /T /C` → `Remove-Item -Recurse -Force` で除去した。以降のタスクで ACL 関連の変異テストを行う場合は、解除処理を壊す変異を避けるか、残留の除去手順を用意してから実施すること
- 検証用の一時フォルダは `%TEMP%` 配下に `gb_` 接頭辞で作る規約になっている（`gb_acl_*` / `gb_lp_*` / `gb_ser_*` など）。残留確認はこの接頭辞で行える
- 「理由・メッセージが入っているか」を検証する箇所では、`IsNullOrEmpty` だと空白のみの値をすり抜ける。タスク3.3の変異テストで実際に見逃しが起き、`IsNullOrWhiteSpace` ＋最小文字数へ強化した。同種の検証では同じ観点に注意すること
- フィクスチャの生成は `%TEMP%` 配下の `gb_fix_*` に作る。生成・削除とも `LongPath.Extend` 経由で、後始末は `RestoreRead` → `Directory.Delete(extendedRoot, recursive: true)` の順（`FixtureBuilder.TearDown`）
- 本体との統合で判明した制約（タスク4.1）: `Helpers/Win32.cs` は internal、`Scanner.GetClusterSize` は private でツールから呼べない。本体を変更せず、`ScanRunner` 内に同一シグネチャの P/Invoke と同一の計算式を持たせて独立に測定している。**本体側の計算が変わるとツールと乖離するため、`scan-performance` で本体を触る際は `ScanRunner.MeasureClusterSize` との整合を確認すること**
- 本体の `Scanner` はアクセス拒否を `catch { }` で握りつぶし、スキップした対象を外部に知らせない。`ScanRunner` は基準フォルダを独立に列挙し直して `UnauthorizedAccessException` の経路のみを記録している。**レビュー指摘（非ブロッキング）: 本体は全例外を握りつぶすがツールは `UnauthorizedAccessException` のみ捕捉するため、別種の例外が起きる状況では非対称になる。** 現在のフィクスチャでは再現しないが、堅牢化を検討すること
- `dotnet build` の増分ビルドはソースの mtime で判定するため、`cp` / `mv` でファイルを復元すると古いキャッシュが使われることがある。一時変異の復元後は `touch` してから再ビルドすること
- 射影ではルートノード自身をエントリに含めない（タスク4.2の判断）。本体の `Scanner.RunScan` が `new FolderInfo(dir.FullName, ...)` でルートの `Name` に絶対パスを格納するため、含めると相対パスに絶対パスが混入する。基準の論理名は `GoldenHeader.BaseFolderLabel` が別途保持する
- 本体の型に触れるツール側のファイルは `Scan/ScanRunner.cs` と `Scan/GoldenProjector.cs` の2つに限定されている。`scan-performance` で `FolderInfo` の構造を変える際は、この2ファイルだけを直せばよい
- 既知の欠落として扱う境界条件は `LongPath` のみ（タスク4.3の判断）。`AccessDenied` は要件2.4・3.4が意図した正常系であり、また本体はサブフォルダのノードを先に親へ追加してから再帰するため、権限のないフォルダ自身は空フォルダとして走査結果に残り欠落しない。`Ordinary` のみを理由とする欠落は「既知の不具合では説明できない」ため列挙しない（要件5.5の正しさ判定に踏み込まないため）。ただしそうした欠落は `BaselineComparer` が `Missing` として別途報告するので握りつぶされない
- サブコマンド（タスク5.1で確定）: `build-fixture` / `generate --out <path>` / `compare --golden <path>` / `update --golden <path>`。共通オプションは `--root <path>`（既定は `%TEMP%\gb_fix_<8桁hex>`）と `--physical-size`（既定 false）。終了コードは一致0 / 差分あり1 / 設定不一致・実行時エラー2
- **終了コードだけを見る検証では副作用（ファイルが書き換わったか）を捕捉できない。** タスク5.1のレビューで、`update` の設定不一致時の書き込み抑止ガードを削除しても79件すべてが通過することが判明し差し戻された。ファイルのバイト列を `SequenceEqual` で照合する項目を追加して解消
- タスク5.1のレビューで非ブロッキングとされた申し送り3件。(a) 基準パスの存在検証は `Program` の事前チェックではなく `ScanRunner.Run` の Precondition の例外伝播に依っている（メッセージは十分具体的だが design.md の Program の責務とは形式的にズレがある）。(b) `Console.OutputEncoding` を UTF-8 固定にした（サブプロセス起動時の文字化け対策）。リダイレクトなしの対話実行での副作用は未検証。(c) `KnownIssueAnalyzer` は `generate` でのみ呼び出す
- **サブエージェントはユーザーのプロセスを停止してはならない。** タスク5.2の実装時、Explorer から起動されていたユーザーの `LargeFolderFinder.exe` がビルドの妨げになり、実装者が停止してしまった。ユーザーのアプリは本体のビルド出力先 `bin\Debug\net48\LargeFolderFinder.exe` から起動されていることがあり、本体の実行ファイルを書き換えるビルドでファイルロック（MSB3027 / MSB3021）が起きる。遭遇したら停止せず、プロセス名と PID を報告して作業を止めること
- `update` の差分あり経路（タスク5.2で検証を追加）: 差分明細が「更新しました」より前に出力されること、明細の値の向き（`期待値=` が現行の期待値、`実際=` が新しい走査結果）、書き換え後の `compare` が一致になることを照合している。**レビューで、明細の期待値と実際を入れ替える変異に反応したのはこの1項目だけで、`compare` 系の既存項目は値の向きを見ていないことが判明した。** `compare` の出力の向きを守る検証は未整備
- 反復生成の同一性（要件2.3、タスク5.3）は**生成日時（`# GeneratedAt:`）の行を除いて**判定する（2026-09-15 ユーザー決定）。要件2.5の生成日時の記録と、繰り返し生成でバイト単位同一という完了条件が衝突したため、完了条件と要件2.3の文言を修正した。`compare` は生成日時を参照しないので比較には影響しない
