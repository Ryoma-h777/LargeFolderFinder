## Implementation Notes
- 1.1: `Tools/ScanBench`（`<path> [--runs N] [--sequential] [--physical-size] [--label TEXT] [--no-digest]`）。出力はタブ区切りで、条件の行（`#`）→ 見出し → 1回ごとの行。要約値は全ノードの相対パス・種別・サイズの SHA-256 の先頭16文字で、ルートの完全パスを含まないため別の場所・別の機の結果と比べられる
- 1.1: メモリの読み方に注意。`Process.PeakWorkingSet64` はプロセスの開始からの最大でリセットできないので、回をまたいで増える。メモリを比べる回は `--no-digest`（要約値の一覧が 45万ファイルで約148MB 押し上げる）かつ `--runs 1`、集計値の一致は別に要約値ありで確かめる
- 1.1: `--threads` と `--buffer` の指定と、並列度・同時の列挙の最大・バッファの列は 3.4 で足す（設計の使い方の記述にはあるが 1.1 では未実装）。`--no-digest` は設計の使い方に無い追加なので、1.3 か 3.4 で設計と手順の記述を実装に合わせる
- 1.2: 基準のコミットは `6c3008c`（利用者が NAS で変更の前を測るときもこれを使う）。物理サイズ換算ありの控えは `artifacts/scan-performance/pre-change-physical.golden.txt`（クラスタサイズ 4096、エントリ21、`compare --physical-size` で一致）。この控えはクラスタサイズ 4096 のドライブでしか一致しない
- 1.2: 変更の前の基準（温まった中央値）: システムドライブ全体（約178万ファイル）が並列 11,612ms・逐次 28,609ms、ファイル数の多いシステムのフォルダ（約21万ファイル）が並列 4,022ms・逐次 9,614ms。要約値の基準は後者の `7cfb52e3f3be418d`
- 1.2: **システムドライブ全体の要約値は前後の比較に使えない**（動いているシステムのドライブなので、走査のたびに総バイト数が増え要約値が変わる）。集計値の不変は、検証ツールの照合と「ファイル数の多いシステムのフォルダ」の要約値で見る
- 1.3: performance.md の計測の手順に、計測の道具の使い方・初回と温まったの区別・中央値での判断・メモリを見る回の `--no-digest --runs 1`・記録の置き場を書いた。前後の比較の表の枠は 1.2 で measurements.md に作ってあるので流用した。確認は親が差分を読んで行った（ドキュメントのみ）
- 2.1: `Models/ScanTuning.cs`（`record ScanTuning(int ThreadCount = 0, int EnumerationBufferSize = 0)`）。`RunScan` の末尾に `ScanTuning? tuning = null`（既存の呼び出し元は無修正で通った）。`ScanProgress` に `WorkerCount` と `PeakConcurrentEnumerations`。`ReportFinalProgress` は今は 0 を載せる（3.2 で実際の値に差し替える）。確認は親が差分を読んで行った
- 2.2: `Services/ScanParallelism.cs`（public。`Resolve` と `IsNetworkPath`）。上限64・ネットワーク16・ローカルは論理プロセッサ数を4〜16に丸めた値は private const で、自己検証は期待値を直接書く（値を変えると試験が落ちて気づける）。2.3 で `Config.txt` に上限を書くときはこの定数と食い違わせないこと。selfcheck は 143 件
- 2.3: `Config.ScanThreads`（既定 0）と `Config.txt` の行・日英の説明。画面は `new ScanTuning(config.ScanThreads)` を渡す。古い `Config.txt`（この行が無い）を新しいアプリが読んでも既定値 0 になる。逆に**新しい `Config.txt` を古い版のアプリが読むと未知のキーで解析に失敗し、設定が既定に戻って警告が出る**（版を戻したときの注意。README で触れる）。selfcheck は 144 件
