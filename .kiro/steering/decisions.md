# 仕様の経緯（決定と却下）

なぜ現在の仕様がこの形なのかを残す。一度試して捨てた案、やらないと決めたこと、決定の理由、要望の由来を扱う。
内容は、旧AIモデルとの開発記録（Git 管理外の `docs/`）から抽出したものである。出典は「フォルダ名／ファイル名」で示す。
記録は当時のものであり、値ではなく理由を残している。現行のコードと食い違う場合はコードを正とする。
このファイルは常時読み込まれる。分量の大きい索引（フォルダごとの扱い、抽出元と抽出先の対応）は、ここに置かずスペック配下に置く（`.kiro/specs/requirements-preservation/inventory.md`、`.kiro/specs/requirements-preservation/mapping.md`）。
見出しの末尾に現行コードとの照合結果を示す。［確認済み］は決定・挙動をコードで確かめたもの、［意図のみ］は記録にしかなくコードから確かめられないもの、［食い違い］は記録とコードが異なるもの（コードを正とし、後続の担当を添える。利用者の判断で現行を正とした、または要望を取り下げたものはその旨を添える）である。
区分は決定・挙動についてのもので、理由はいずれの区分でも記録に由来し、コードでは確かめていない。

## 一度試して捨てた案

### 高速キャッシュモード（スキャン時に前回の結果を再利用する） ［確認済み］
- 試したこと: スキャン時にキャッシュファイルを読み込み、有効期限つきで前回のスキャン結果を再利用して高速化するモード。画面の「キャッシュを利用」チェックボックス、専用のキャッシュファイル、有効期限の定数まで実装した
- 捨てた理由: 正確性の確保が難しく、利用者の混乱を招くおそれがあり、複雑化するため。関連するコードをすべて削除し、スキャンのたびに常に最新の情報を取得する構成に戻した
- 再提案の条件: 「スキャンは常に最新を取得する」という方針に反する形、つまりスキャンの結果として保存済みの結果を読んで使い回す形では再提案しない
- 範囲の注意: 捨てたのはスキャン時の再利用だけである。前回の結果を保存し、再起動後に再スキャンせず表示する機能は、後に別の要望で入っている（`Cache_Result_Persistence/implementation_plan.md`）
- 出典: `Code_Refactoring_and_Cache/implementation_plan.md`, `Code_Refactoring_and_Cache/walkthrough.md`

### 実行基盤の移行に伴って外れた、.NET 9 の自己完結型・単一ファイルの発行設定 ［確認済み］
- 性質: 配布形態として評価して退けた案ではなく、実行基盤の移行に付随して外れた設定である
- 外れた設定: .NET 9 を対象とした発行設定にあった、自己完結型・単一ファイルの指定
- 外れた経緯: 実行基盤を Windows 10/11 に標準搭載の .NET Framework 4.8 へ移すのに伴い、発行設定から削除した。記録は移行の目的として、利用者がランタイムを別途インストールせずに済むことと、実行ファイルの劇的な軽量化を挙げる。自己完結型と比べてファイルサイズが小さいことは、配布手順の記録も利点として明示する（`Git_Initialization/walkthrough.md`）
- 範囲の注意: 記録にあるのは、実行基盤を .NET Framework 4.8 に移すのに伴う発行設定の削除だけで、自己完結型・単一ファイルの配布そのものを退けた判断は記録にない
- 補足: 移行後の実行基盤では、依存 DLL を EXE に埋め込む形で単一ファイルの配布を実現している（`Runtime_Downgrade_v2/walkthrough.md`）
- 同じ設定に戻すことの可否: 記録には書かれていない
- 出典: `Runtime_Downgrade/implementation_plan.md`, `Runtime_Downgrade/walkthrough.md`

### 古い実行基盤に合わせてコードの書き方を古くする移行（1回目の移行） ［食い違い］
- 試したこと: .NET Framework 4.8 への1回目の移行で、フォルダ選択ダイアログの処理を新設のヘルパーファイルに分け、ファイルスコープ名前空間を従来のブロック形式へ書き換えた
- 捨てた理由: 1回目の移行は「仕様が壊れた」という課題になった。やり直しでは、新しい言語バージョンを指定して新しい構文を保ち、コードの可読性を損なわないようにした。記録は、何が壊れたかを具体的には書いていない
- 再提案の条件: 古い実行基盤への対応を理由に、新しい構文を古い形へ書き換えること
- 範囲の注意: やり直しではヘルパーファイルを作らなかったが、その理由はプロジェクト構造の簡素化と標準的な WPF の作法であり、記録はヘルパーを壊れた原因とは書いていない。別の記録にはダイアログ専用のファイルが出てくる（`fix_scan_completion_display/implementation_plan.md`, `fix_scan_completion_display/walkthrough.md`）。ダイアログ処理を別のファイルや型に分けることは、この項目の対象外である
- 現行コードとの食い違い: 現行コードの名前空間は、すべてブロック形式である。新しい言語バージョンの指定と、ほかの新しい構文は保たれている。後続の担当: `architecture-refactoring`

### タブを均等幅で並べる ［確認済み］

## 明示的な非目標（やらないと決めたこと・求めないこと）

- 理由: 正確性の確保が難しく、利用者の混乱と複雑化を招くため（詳細は上の「高速キャッシュモード」）

- 理由: 一般の利用者が不用意に触れないようにし、画面を簡潔で安全に保つため（`advanced_config_and_speed/implementation_plan.md`, `advanced_config_and_speed/walkthrough.md`）
- 範囲: 記録が画面から外したのは並列スキャンのチェックボックスである。同じ記録で設定ファイルへ移した他の項目は、コード内の定数から移したもので、画面から外したものではない

## 決定とその理由

### 上級者向けの設定は、起動したままでも書き換えを反映する ［確認済み］
- 決定: 設定ファイルを起動時に加えてスキャンの開始時にも読み直す。テキストエディタで開いたままでも読めるように読み込む
- 理由: アプリを起動したまま設定を書き換えて試行錯誤できるようにするため。エディタで開いたままの読み込みは計画とタスク一覧に書かれ、実施記録にはない
- 出典: `advanced_config_and_speed/implementation_plan.md`, `advanced_config_and_speed/task.md`, `advanced_config_and_speed/walkthrough.md`

### 設定ファイルを開くボタンは目立たせない ［確認済み］
- 決定: 設定ファイルを既定のエディタで開くボタンを置き、ファイルがなければ既定値で作ってから開く。外観は小さく目立たないものにした
- 理由: 設定ファイルを簡単に編集・確認できるようにするため。目立たない外観は、画面の邪魔にならないようにするため
- 出典: `config_open_button/implementation_plan.md`, `config_open_button/walkthrough.md`

### タブを閉じたら、そのタブの保存ファイルも消す ［確認済み］
- 決定と理由: ディスク使用量が増え続けるのを防ぐため、タブを閉じたときにそのタブの結果の保存ファイルを削除する
- 出典: `Cache_Cleanup_20260123/implementation_plan.md`, `Cache_Cleanup_20260123/task.md`

### ウィンドウの状態は、最小化のままでは復元しない ［食い違い］
- 決定: 終了時にウィンドウの位置・サイズ・状態を保存し、次回に復元する。最大化中に終えたときは元のサイズを保ったうえで最大化として記録する。最小化中に終えたときは元のサイズを保ち、次回は通常の状態で開く
- 理由: 最小化のまま起動するのを防ぐため。最大化中に元のサイズを保つ理由は記録に書かれていない
- 現行コードとの食い違い: 現行コードは終了時に位置・サイズ・状態を保存するが、次回の起動時にそれを読んで復元する処理がない（480e4d3 で削除。公開版ではまだ動いている）。後続の担当: `architecture-refactoring`（利用者の判断により、消えた要望の復元を例外として扱う）
- 出典: `SavingWindowGeometry/implementation_plan.md`, `SavingWindowGeometry/walkthrough.md`

### 起動時の例外は、内容を画面に出す ［確認済み］
- 決定: ウィンドウの初期化で例外が起きたら、内容をメッセージボックスで表示する。初期化の途中で発火したイベントは、コントロールが揃うまで処理を飛ばす
- 理由: 原因不明のままアプリが消えないようにするため。イベントの処理を飛ばすのは、初期化中のイベントが未生成のコントロールに触れて起動しなくなった不具合への対策
- 出典: `startup_fix_and_stability/implementation_plan.md`, `startup_fix_and_stability/walkthrough.md`

### 管理者として開き直す ［食い違い］
- 決定: メニューから、UAC を経て管理者権限で開き直せるようにする。既に管理者として動いているときは項目を無効にする。UAC で拒否されたときは今のプロセスをそのまま続ける
- 理由: ごみ箱や、システム権限が必要なフォルダをスキャンする際に便利なため。無効にすることと、拒否時に続けることの理由は記録に書かれていない
- 補足: 管理者のときの扱いを、タスク一覧の UI の節は「無効化または非表示（オプション）」とし、同じタスク一覧のロジックの節と、計画・実施記録は無効化とする
- 現行コードとの食い違い: 現行コードには、管理者として動いているときに項目を無効にする処理も、非表示にする処理もない（1cd6081 で失われた）。メニューから開き直すことと、UAC で拒否されたときに今のプロセスを続けることは一致する。後続の担当: `architecture-refactoring`（利用者の判断により、消えた要望の復元を例外として扱う）
- 出典: `Admin_Restart/implementation_plan.md`, `Admin_Restart/task.md`, `Admin_Restart/walkthrough.md`

### メニューバーを置く ［確認済み］
- 決定と理由: Windows アプリらしい標準的な操作性のため、ウィンドウ上部にメニューバーを置いた
- 出典: `Add_Menu_Bar/implementation_plan.md`, `Add_Menu_Bar/walkthrough.md`

### タブと共通操作の分担 ［確認済み］
- 決定: パス入力とスキャンの操作はタブの外の上部に共通で置き、常にアクティブなタブに作用させる。スキャン条件（パスと閾値）・表示設定・結果はタブごとに持つ。縦横のレイアウトは全タブ共通とする
- 理由: 「タブを切り替えると表示設定と結果が切り替わる」という要件から、スキャン条件もタブが持つのが正しいと計画が判断した。パス入力の位置は共通だが、値はタブに従う。レイアウトを全タブ共通にする理由は記録に書かれていない
- 補足: スキャンを新規タブで実行する案との関係は「小さな選択」を参照。記録はアクティブなタブを更新する挙動を「今回は」基本とし、パスが変わっている場合の扱いを検討事項として残している
- 出典: `TabbedInterface/implementation_plan.md`, `TabbedInterface/task.md`

### 描画の取り消しを、タブ間で干渉させない ［食い違い］
- 決定と理由: 結果の描画の取り消しが全体で1つだとタブ間で干渉するため、取り消しをタブごとに持つ
- 現行コードとの食い違い: 現行コードはタブごとに描画の取り消しを持つ欄を残しているが、描画の処理はそれを使っておらず、描画を取り消さない。後続の担当: `scan-correctness`（`architecture-refactoring` の死んだコードの除去で、未使用の取り消しの欄が消されるおそれがある）
- 出典: `fix_rendering_and_status_behavior/implementation_plan.md`, `fix_rendering_and_status_behavior/walkthrough.md`

### コピー完了の通知は、進捗の表示を消さない ［確認済み］
- 決定と理由: 左側の進捗や経過時間の表示を保ったまま知らせるため、通知は状態表示の欄の右側に設けた専用の領域に短い間だけ出す
- 出典: `clipboard_copy_feature/implementation_plan.md`, `clipboard_copy_feature/walkthrough.md`

### 進捗率は、事前カウントした範囲で数える ［確認済み］
- 決定: 事前カウントを一部の階層に限るのに合わせ、スキャン中の進捗もその範囲のフォルダだけを数える
- 理由: 進捗率と事前カウントの数を整合させるため。100% に達した時点は「全体の構造の把握が終わり、詳細をスキャン中」という意味になる
- 出典: `scan_optimization/implementation_plan.md`, `scan_optimization/walkthrough.md`

### 事前カウントを省いたときは、残り時間を出さない ［確認済み］
- 決定と理由: 事前カウントを省くと総数が分からず残り時間を計算できないため、残り時間は出さず経過時間を出す
- 出典: `skip_count_feature/implementation_plan.md`, `skip_count_feature/walkthrough.md`

### 完了時の処理時間と、検索サイズの引き継ぎ ［食い違い］
- 決定: 完了時の処理時間は、経過時間の長さに応じて「時間・分・秒」「分・秒」「秒」「ミリ秒」の形を切り替えて表示する。検索サイズは次回の起動時に引き継ぐ
- 理由: 利用者の利便性を上げるため
- 現行コードとの食い違い: 現行コードは1時間を超えると「時間・分」の形で表示し、秒を出さない（1cd6081 で失われた）。形の境目は記録の「以上」に対してコードは「超える」で、ちょうど1時間などの境目では1段下の形になる。検索サイズの引き継ぎ（現行はタブごとの保存ファイルによる）は一致する。後続の担当: `architecture-refactoring`（利用者の判断により、消えた要望の復元を例外として扱う）
- 出典: `settings_and_status/implementation_plan.md`, `settings_and_status/walkthrough.md`

### 設定の YAML 化に付随して外れた JSON 依存（記録どうしが食い違う） ［確認済み］
- 性質: 決定ではない。記録にあるのは、YAML への移行と統一に付随して JSON への依存が外れたことだけで、評価して JSON を避けると決めた記録はない
- 記録の内容: 設定ファイルを YAML に移した際、設定と保存データの部分で JSON への依存を排除したと記録する（`yaml_config_migration/walkthrough.md`）。実行基盤の移行のやり直しでは、設定・言語ファイルとも YAML に統一したのに伴い、JSON への依存も完全に排除したと記録する（`Runtime_Downgrade_v2/walkthrough.md`）
- 食い違い: `Runtime_Downgrade_v2/walkthrough.md` は同じ文書の中で「System.Text.Json などの不足パッケージを追加」とも書く。1回目の移行も、JSON 処理を続けるためにこのパッケージを追加したと記録する（`Runtime_Downgrade/walkthrough.md`）。どれが最終の状態かは記録から判断できない。現行コードは JSON のパッケージに依存しておらず、「排除した」とする記録と一致する

## 要望に由来する仕様

記録が利用者の要望・指示・レビューでの指摘と明示しているものだけを載せる。

### 再起動後も、再スキャンせずに前回の検索結果を使う ［確認済み］
- 要望: 再スキャンせずに、再起動時に検索結果を使いたい。複数の検索セッション（将来のタブ機能）も支えたい
- 導かれた仕様: 最後の設定だけでなく、検索セッションごとの条件と結果を保存する。記録上の保存の構造（1つのファイル内のセッションの一覧）は、後にタブごとのファイルへの分割に置き換わった（`Cache_Optimization/walkthrough.md`）
- 出典: `Cache_Result_Persistence/implementation_plan.md`, `Cache_Result_Persistence/walkthrough.md`

### 単位を切り替えたら閾値を換算し、ラベルから単位を外す（レビューでの指摘） ［食い違い］
- 要望: 単位を切り替えたら、入力済みの閾値を新しい単位に自動で換算する。検索サイズのラベルから単位の表記を外す
- 食い違い: `Unit_Localization` は、単位を切り替えてもラベル・ツールチップ・スキャン中のメッセージに「GB」が固定で残る問題を、言語ファイルに単位の差し込み位置を設けて直し、ラベルに選択中の単位を出す形にした。ラベルから単位を外す指摘と逆の扱いで、どちらが後かは記録から読み取れない（`Unit_Localization` はタスク一覧が未完了のまま、実施記録は完了と報告する）

### 1000進と1024進の単位を使い分ける ［食い違い］
- 要望: 1000進（KB 系）と1024進（KiB 系）の単位を使い分けたい
- 導かれた仕様: 両方の単位を併存させた。既定の単位は、Windows の内部の計算方式（1024進）に合わせて GiB とした
- 補足: この要望より前の `Unit_Switching` の記録では、単位は KB〜TB の4種で、GB を1024進として換算していた。この要望で、KB 系は1000進の意味に定義し直された
- 現行コードとの食い違い: 現行コードに1024進の KiB 系の単位はない。コードで確認した現行の単位は B と KB〜TB で、いずれも1024進で換算し、既定は GB である。KiB 系はコードの履歴にも出てこない。後続の担当: 利用者の判断により要望を取り下げる（2026-09-17）。実装されなかった
- 出典: `unit_redefinition/implementation_plan.md`, `unit_redefinition/walkthrough.md`, `Unit_Switching/implementation_plan.md`, `Unit_Switching/walkthrough.md`, `Unit_Switching/task.md`
