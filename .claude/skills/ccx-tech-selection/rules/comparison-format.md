# comparison-format.md

Output format definition for `tech-selection.md` generated by the `ccx-tech-selection` skill.
The Report Generator (Step 5) MUST follow every rule in this file when constructing the report.

---

## Header

The opening section of `tech-selection.md` MUST contain:

```markdown
# Technology Selection Report: {feature}

- **Feature**: {feature}
- **Generated**: {ISO 8601 datetime, e.g. 2026-05-29T14:30:00+09:00}
```

No other frontmatter or metadata format is permitted.

---

## Comparison Table

For **each technology category** that has two or more candidates (`status: "needs-comparison"`),
render a Markdown table with the following columns in this exact order:

| Column | Description |
|--------|-------------|
| Candidate | Library / framework / language name |
| Version | Latest stable version at time of research |
| License | SPDX license identifier (e.g., MIT, Apache-2.0, GPL-3.0) |
| Maintenance | `Active` if a release exists within the last 6 months; otherwise `Inactive` |
| Key Advantages | Up to three concise bullet points of notable strengths |
| Key Concerns | Up to three concise bullet points of notable drawbacks or risks |

Place a reference row below the table in the following format:

```
> Sources: {comma-separated list of URLs or source names per candidate}
```

### Special Case — Single Candidate

When a category has exactly one candidate (confirmed by `tech.md` constraint or business mandate),
**skip the comparison table entirely** and output the following line instead:

```
**Pre-selected**: {CandidateName} (Reason: {constraint description})
```

### Special Case — Confirmation-Only Mode

When ALL categories are already confirmed by steering (`mode: "confirmation-only"`),
**skip the Comparison Table, Adoption Decision, and Rejection Reasons sections entirely**.
Output only the confirmed technology stack list in the following format:

```markdown
## Confirmed Technology Stack

| Technology | Version | Confirmed By |
|------------|---------|-------------|
| {name} | {version} | {tech.md reference} |
```

Then proceed directly to the [Design Integration Summary](#design-integration-summary) section
(which MUST still be present even in confirmation-only mode).

---

## Adoption Decision

For each technology category that was compared, include a subsection:

```markdown
### {Category Name}

**Adopted**: {CandidateName}

{Reason paragraph — 2 to 3 sentences explaining why this candidate was selected.}
```

#### Evaluation Priority Order

Adoption decisions MUST be made according to the following priority, from highest to lowest:

1. **tech.md explicit constraint** (highest priority) — If `tech.md` mandates a specific technology,
   select it regardless of other factors.
2. **License type** — Prefer permissive licenses (MIT, Apache-2.0, BSD). Accept GPL/LGPL only with
   an explicit risk warning (see below). Reject candidates with proprietary or unclear licenses
   when a permissive alternative exists.
3. **Maintenance status** — Prefer `Active` candidates over `Inactive` ones.
4. **Community adoption rate** (lowest priority) — Prefer the candidate with the larger user base
   and ecosystem when all higher-priority criteria are equal.

#### GPL / LGPL License Warning

When the adopted candidate carries a GPL or LGPL license, append the following warning block
**immediately after** the adoption reason paragraph:

```markdown
> **License Risk Notice**: This package is licensed under {GPL/LGPL variant}.
> Depending on how it is linked or distributed, your project may be subject to
> source-disclosure obligations and combination restrictions.
> Verify compatibility with your project's distribution model before proceeding.
```

---

## Rejection Reasons

For each category that was compared, list every **non-adopted** candidate with at least one
sentence explaining why it was not selected:

```markdown
### {Category Name} — Rejected Candidates

- **{CandidateName}**: {One or more sentences stating the primary rejection reason.}
- **{CandidateName}**: {One or more sentences stating the primary rejection reason.}
```

If a category had only one candidate (pre-selected format was used), **omit this section
for that category**.

---

## Design Integration Summary

This section MUST always appear at the end of `tech-selection.md`, regardless of mode
(comparison, confirmation-only, or mixed).

Its purpose is to provide a pre-researched Technology Stack table that the developer
(or whichever design-generation step they use next, e.g. `/kiro-spec-design`) can carry
over directly into the `design.md` Technology Stack section format. `ccx-tech-selection`
does not read or modify `design.md` itself, and does not assume any particular
design-generation skill is installed — this table is a standalone hand-off artifact.

Render the table as follows:

```markdown
## Design Integration Summary

| Layer | Technology / Version | Role in Feature | Notes |
|-------|---------------------|-----------------|-------|
| {layer} | {name} {version} | {what it does in this feature} | {optional caveats or warnings} |
```

Rules for this table:

- **Layer**: Use a short descriptive label such as `Language`, `Framework`, `HTTP Client`,
  `Database ORM`, `Testing`, etc. Match the granularity of the `design.md` Technology Stack table.
- **Technology / Version**: Combine the adopted technology name and its version in one cell
  (e.g., `Python 3.12`, `FastAPI 0.111`).
- **Role in Feature**: One concise phrase describing how this technology is used within the
  feature being specified (not a general description of the technology).
- **Notes**: Optional. Use this cell for license risk warnings, deprecation notices, or
  version-pinning requirements. If none apply, leave the cell empty or write `—`.

When generating `design.md`'s Technology Stack section, use this table as the **primary source**
of pre-researched technology choices, and avoid contradicting it without a documented reason.
