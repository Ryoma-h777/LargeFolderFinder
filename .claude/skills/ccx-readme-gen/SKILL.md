# ccx-readme-gen

## Overview

ccx-readme-gen generates an end-user README from the spec documents. It targets the
**whole project (workspace)** and does not require a specific feature (the spec that the
README is based on is auto-resolved). The output format (extension) is proposed according to
the distribution shape and finalized after developer confirmation (the same
distribution-shape-based approach as `ccx-thirdlicense-gen`). It can run standalone,
independently of `ccx-build-package`.

**Execution flow:**
1. Auto-resolve the source spec → collect information from the spec documents (basic info, overview, usage, system requirements, installation steps, other important info)
2. Duplication check against in-app guidance
3. Propose the output format and confirm with the developer (main viewing channel × image necessity → md/html/txt)
4. Assemble and emit README.{ext} (project root, including third-party license reference guidance)

## Usage

```
/ccx-readme-gen

例:
  /ccx-readme-gen
```

**Arguments:**
- None (this skill targets the whole project; the source spec is auto-resolved)

## Rule files

- `rules/content-collection.md` — collect information from the spec documents
- `rules/duplication-check.md` — duplication check against in-app guidance
- `rules/format-selection.md` — two-axis judgment of main viewing channel × image necessity; propose the output format (extension) and confirm with the developer
- `rules/readme-assembly.md` — assemble README.{ext} (per-format rendering) and third-party license reference guidance

## Output

- **Console**: the resolved source spec, a summary of collected info, duplication-check results, the finalized output format, generation result
- **Files**: project-root `README.{ext}` (extension finalized by distribution shape; copied into the Release directory when `ccx-build-package` runs)

## Step 1: Resolve Source Spec

This skill takes no feature argument. It auto-resolves the spec the README is based on.

1. Enumerate specs via Glob `.kiro/specs/*/spec.json`.
2. **0 found** → display the following error and **stop immediately**:
   ```
   エラー: .kiro/specs/ に spec が見つかりません。
   先に `/kiro-spec-init <feature-name>` を実行してスペックを初期化してください。
   ```
3. **1 found** → adopt that spec automatically as the source (`{spec}`).
4. **Multiple found** → present the list and confirm with the developer which spec the README
   is based on (if `.kiro/steering/roadmap.md` has a Specs list, attach the dependency order as
   reference). Wait for the answer, then finalize `{spec}`.

Retain the finalized `{spec}` as the source directory for later steps. Display the result before proceeding:
```
情報源 spec: <spec>
```

---

## Step 2: Content Collection

1. Read `.claude/skills/ccx-readme-gen/rules/content-collection.md`.
2. Read `.kiro/specs/{spec}/spec.json`, `design.md`, `requirements.md`.
3. Apply the rules to produce the `CollectedContent` structure (basic info, overview, usage, system requirements, installation necessity, other important info).
4. If installation necessity or developer info cannot be determined, follow the rule file's guidance (ask the developer or insert a placeholder — do not guess silently).

> The version number is read from the project-root `VERSION` file (not from spec.json).

---

## Step 3: Duplication Check

1. Read `.claude/skills/ccx-readme-gen/rules/duplication-check.md`.
2. Apply the rules to classify usage / system requirements / installation (only if required) as `duplicate-confirmed`, `unique`, or `unclear`.
3. For any `unclear` item, ask the developer and wait for the answer before proceeding to the next step.

---

## Step 4: Format Selection

1. Read `.claude/skills/ccx-readme-gen/rules/format-selection.md`.
2. Apply its two-axis model: identify the **main viewing channel** (renderer / browser / plaintext — ask the developer when multiple channels compete or none is determinable) and whether **images are needed**, then derive the proposed extension (`.md` / `.html` / `.txt`) from the channel×images table. Handle the plaintext×images conflict by presenting the html-or-txt choice.
3. Present the proposal and reasoning (including any image-shipping note) to the developer and wait for explicit confirmation (or an alternative extension) before proceeding. **Never finalize the format without this confirmation**, even for unambiguous cases.

---

## Step 5: Assembly and Output

1. Read `.claude/skills/ccx-readme-gen/rules/readme-assembly.md`.
2. Apply the rules to assemble the final `README.{ext}` in the confirmed format, incorporating the duplication-check decisions and referencing the project-root `THIRD_PARTY_LICENSES.*` (via Glob) if present.
3. Run the self-check defined in the rules file.
4. Write the result to the project-root `README.{ext}` using the confirmed extension. Emit only that one file.

## Output Description

Provide output in Japanese:

1. **情報源 spec**: 自動特定または確認で確定した spec 名
2. **収集サマリー**: 基本情報・概要・使い方・動作環境の収集結果
3. **重複判定結果**: 各項目の判定（duplicate-confirmed / unique）
4. **出力形式**: 提案と確認結果（確定した拡張子）
5. **生成結果**: ファイルパス、自己点検の結果
6. **最終レポート**: 第三者ライセンス参照状況

## Safety & Fallback

### Error Scenarios

- **No spec (Step 1)**: prompt `/kiro-spec-init` and stop
- **Multiple specs, subject undecided (Step 1)**: present the list and confirm with the developer (wait for the answer, then continue)
- **No version info in the VERSION file**: state "バージョン情報未確定" explicitly and continue
- **No developer info in the spec documents**: insert a placeholder and continue
- **In-app guidance presence indeterminable**: confirm with the developer and wait for the answer before continuing (do not omit unilaterally)
- **Viewing channel indeterminable / no primary among multiple channels (Step 4)**: ask the developer directly and wait for the answer before finalizing the format (do not decide unilaterally)
- **Plaintext channel but images are required (Step 4)**: present it as a conflict and have the developer choose "convert to html" or "txt without images"
- **THIRD_PARTY_LICENSES not generated**: insert guidance prompting `ccx-thirdlicense-gen` and continue

### Boundary Notes

- This skill targets the whole project and takes no feature name. The source spec is auto-resolved.
- It does not generate the `THIRD_PARTY_LICENSES` file itself (that is `ccx-thirdlicense-gen`'s responsibility).
- It does not orchestrate the whole distribution package, manage versions, or zip (that is `ccx-build-package`'s responsibility).
- The README output format is **variable by main viewing channel × image necessity** (md/html/txt). The channel is the primary decision axis; images are a constraint (excluding txt, deciding the bundle/embed method). The propose + developer-confirm approach is shared with `ccx-thirdlicense-gen` (see research.md). Do not generate without finalizing the format. The output goes to the project root.
- The spec documents are read-only. Writes are limited to the project-root `README.{ext}` (a single file with the finalized extension).
