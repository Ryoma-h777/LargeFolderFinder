# ccx-build-package

## Overview

ccx-build-package packages a tool developed with cc-sdd into a distributable state.
It targets the **whole project (workspace)** and does not require a specific feature.
It requires `ccx-security-check` Gate 3 (the pre-distribution final review) to be a GO,
and orchestrates the subsequent distribution-prep work as a fixed-order pipeline.

`THIRD_PARTY_LICENSES` is generated by `ccx-thirdlicense-gen` and the README by
`ccx-readme-gen`. This skill only confirms that those deliverables (at the project root)
exist; it holds no generation logic of its own.

**Pipeline:**
1. Prerequisite checks (auto-resolve specs, confirm Gate 3 GO)
2. Version management (based on the VERSION file, auto-increment, reflect into manifest.json)
3. Deliverable check (confirm project-root THIRD_PARTY_LICENSES.* / README.* exist)
4. CHANGELOG.md generation
5. Distribution-directory assembly, zipping, and checklist report

## Usage

```
/ccx-build-package

例:
  /ccx-build-package
```

You must run `/ccx-thirdlicense-gen` and `/ccx-readme-gen` beforehand.

**Arguments:**
- None (this skill targets the whole project)

## Rule files

- `rules/version-management.md` — version read/increment/multi-file propagation (based on the VERSION file)
- `rules/deliverable-check.md` — confirm project-root THIRD_PARTY_LICENSES.* / README.* exist (no generation)
- `rules/changelog-gen.md` — CHANGELOG.md generation (Keep a Changelog format)
- `rules/package-assembly.md` — distribution-directory assembly, zipping, checklist report

## Output

- **Console**: per-step progress, final verdict (ready / not recommended), next actions
- **Files**:
  - project-root `VERSION` (source of truth), `manifest.json` (when present)
  - project-root `CHANGELOG.md`
  - `Release/{tool-name}-{version}/` (distribution payload = full product files, README.*, LICENSE, THIRD_PARTY_LICENSES.*, CHANGELOG.md)
  - `Release/{tool-name}-{version}.zip`

## Step 1: Prerequisite Checks

### 1.1 Resolve Target Specs

This skill targets the whole project, so it takes no feature argument. It does, however,
reference `.kiro/specs/` as the source for the Gate 3 verdict, `tool-name`, and output language.

1. Enumerate specs via Glob `.kiro/specs/*/spec.json`.
2. **0 found** → display the following error and **stop immediately**:
   ```
   エラー: .kiro/specs/ に spec が見つかりません。
   先に `/kiro-spec-init <feature-name>` を実行してスペックを初期化してください。
   ```
3. **1 or more found** → retain all discovered specs as "the specs that make up the project to distribute."
   - Select one representative spec for `tool-name` / output language. If there is a single
     spec, use it; if there are several, present the spec list and confirm with the developer
     (if `.kiro/steering/roadmap.md` has a Specs list, attach the dependency order as reference).

### 1.2 Check Security Gate 3 Result

Because distribution targets the whole project, **every existing spec** must have a Gate 3
GO. For each spec enumerated in 1.1, check `.kiro/specs/{spec}/security-report-review.md`.

- If `security-report-review.md` is **absent** for any spec, display the following and **stop immediately**:
  ```
  エラー: .kiro/specs/<spec>/security-report-review.md が見つかりません。
  配布前に Security Gate 3 の通過が必要です。先に `/ccx-security-check <spec> review` を実行してください。
  ```
- If present, Read it and confirm the final verdict. The report's final verdict line uses the
  `ccx-security-check` format (`✅ GO` / `❌ NO-GO`). Take care not to mistake `NO-GO` for a GO.
- If any spec's verdict is **not GO** (NO-GO or indeterminable), display the following and **stop immediately**:
  ```
  エラー: Security Gate 3 が GO 判定ではありません（spec: <spec>, 現在: <verdict>）。
  配布前に指摘事項を修正し、`/ccx-security-check <spec> review` を再実行して GO を得てください。
  ```

### 1.3 Show Startup Header and Proceed

Once all prerequisite checks pass, display the startup header and proceed to Step 2:

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 ccx-build-package
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Security Gate 3: ✅ GO 確認済み（全 spec）
配布パッケージの作成を開始します。
```

---

## Step 2: Version Management

1. Read `.claude/skills/ccx-build-package/rules/version-management.md`.
2. Apply its rules to read the current version from the project-root `VERSION` file, determine the next version, present any major-version suggestion, and propagate the confirmed version to the `VERSION` file and `manifest.json` (if present).
3. Retain the **confirmed version** string; every downstream step (release directory name, CHANGELOG entry, zip name) uses it.

Do not hardcode version logic in this file — the rules file is the single source of truth.

---

## Step 3: Deliverable Check (THIRD_PARTY_LICENSES / README)

1. Read `.claude/skills/ccx-build-package/rules/deliverable-check.md`.
2. Apply its rules to confirm the project-root `THIRD_PARTY_LICENSES.*` and `README.*` both exist.
3. If either is missing, display the corresponding error from the rules file and **stop immediately** — do not attempt to generate either file yourself. Generation is entirely out of this skill's boundary (`ccx-thirdlicense-gen` / `ccx-readme-gen`).
4. If both are found, retain their exact paths (including the actual extensions of both `THIRD_PARTY_LICENSES.*` and `README.*`) for the Package Assembler.

---

## Step 4: CHANGELOG.md Generation

1. Read `.claude/skills/ccx-build-package/rules/changelog-gen.md`.
2. Use the Bash tool to retrieve the git commit log, classify commits into Keep a Changelog categories, and format the new version entry.
3. Write/Edit the project-root `CHANGELOG.md`, inserting the new version entry at the top.

---

## Step 5: Package Assembly and Report

1. Read `.claude/skills/ccx-build-package/rules/package-assembly.md`.
2. Build `Release/{tool-name}-{version}/`. First copy in the **distribution payload** — the product files themselves, per the rules file's Step 2.0 (for a file-based product such as this skill framework: the `.claude/skills/ccx-*/` directories only, install paths preserved — **nothing under `.kiro/`**, which is cc-sdd/kiro territory; compiled executables/installers remain developer-placed with guidance). Then copy the project-root `README.*` and `THIRD_PARTY_LICENSES.*` confirmed in Step 3 (using their actual extensions), and the root `CHANGELOG.md` and `LICENSE`.
3. Verify the mandatory deliverables exist — **including the payload for a file-based product** — then create `Release/{tool-name}-{version}.zip` via PowerShell `Compress-Archive` (Bash tool).
4. Confirm the distribution checklist and display the final report (checklist table + overall verdict).

### Final Verdict

- If all mandatory checklist items are satisfied:
  ```
  ✅ 配布パッケージを作成しました: Release/<tool-name>-<version>.zip
  配布チェックリストの必須項目はすべて満たされています。
  ```
- If any mandatory item is unmet:
  ```
  ⚠️  配布パッケージは作成しましたが、必須チェック項目に未達成があります: <items>
  配布前に解消することを推奨します。
  ```

## Output Description

Provide output in Japanese:

1. **各ステップの進捗**: 前提確認結果、確定バージョン、生成物確認結果、CHANGELOG 更新結果
2. **最終レポート**: 配布チェックリストの結果テーブル（✅/⚠️/❌）と総合判定
3. **成果物**: `Release/{tool-name}-{version}/` の内容と zip のパス

## Safety & Fallback

### Error Scenarios

- **No spec (1.1)**: prompt `/kiro-spec-init` and stop
- **security-report-review.md absent (1.2)**: prompt `/ccx-security-check <spec> review` for that spec and stop
- **Any spec not GO (1.2)**: prompt for remediation and a Gate 3 re-run, then stop
- **VERSION file invalid/absent (Step 2)**: show a warning and restart numbering from `0.1.0.0`, then continue
- **No `version` field in manifest.json (Step 2)**: show a warning, update only VERSION, and continue
- **THIRD_PARTY_LICENSES.* absent (Step 3)**: prompt `/ccx-thirdlicense-gen` and stop
- **README.* absent (Step 3)**: prompt `/ccx-readme-gen` and stop
- **git log retrieval fails (Step 4)**: show a warning and continue with an empty CHANGELOG entry
- **Missing mandatory deliverable (Step 5, except LICENSE)**: show an error and stop. A missing LICENSE is a warning only and continues
- **Distribution checklist unmet (Step 5)**: enumerate the unmet items and warn that distribution is not recommended (the process itself completes)

### Boundary Notes

- This skill targets the whole project and takes no feature name. `.kiro/specs/` is used only to reference the Gate 3 verdict, tool-name, and output language (read-only).
- This skill runs no compiler or build command. Placing build-requiring executables/installers is the developer's responsibility. Build-free file deliverables (skill directories, etc.) are copied by this skill as the distribution payload (rules/package-assembly.md Step 2.0).
- It performs no security validation. It only references the Gate 3 result (GO/NO-GO) as a prerequisite.
- It does not detect dependency licenses or generate `THIRD_PARTY_LICENSES` (that is `ccx-thirdlicense-gen`'s responsibility).
- It does not generate the README (that is `ccx-readme-gen`'s responsibility).
- The user decides the major version (the AI only proposes).
- The source of truth for the version is the project-root `VERSION` file. Writes are limited to Release/, CHANGELOG.md, `VERSION`, and `manifest.json` (its `version` field when present). It does not write a version into `.kiro/specs/{feature}/spec.json`.
- Numbering in-progress local development builds is `ccx-version-manage`'s responsibility (this skill only finalizes releases).
