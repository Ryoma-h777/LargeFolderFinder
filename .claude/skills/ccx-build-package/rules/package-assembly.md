# Package Assembly Rules

Defines how ccx-build-package builds the distribution directory, produces the zip archive, and reports against the distribution checklist. Referenced by SKILL.md at runtime (Read tool).

Directory structure and checklist basis: `.kiro/steering/distribution.md`.

## Step 1: Resolve Names

- `tool-name`: resolve the distribution/product name in this priority order, using the first
  that yields a usable value: `manifest.json` の `name` → `package.json` の `name` →
  Step 1.1 で選んだ代表 spec 名（`.kiro/specs/{spec}/spec.json` の feature 名） →
  プロジェクトルートのディレクトリ名。Use a filesystem-safe kebab-case value.
- `version`: the confirmed version from the version-management step.
- Distribution directory: `Release/{tool-name}-{version}/` (the project-root distribution
  folder is named `Release` — never `dist`, which reads as an intermediate build output)
- Archive: `Release/{tool-name}-{version}.zip`

## Step 2: Build the Distribution Directory

Create `Release/{tool-name}-{version}/` and place the artifacts below.

### Step 2.0 — Distribution payload (the product itself; mandatory)

A package that lacks the product files is defective, no matter how complete the
documentation set is. Resolve the payload first:

- **File-based product** (the distributable is a set of files needing no compilation —
  e.g. this framework: the `ccx-*` skill set): copy the product files into the
  distribution directory **preserving their install-relative paths** so the recipient can
  copy-merge them. For the ccx skill set that is:
  - `.claude/skills/ccx-*/` — all ccx skill directories (cc-sdd core `kiro-*` skills are
    **excluded**; the recipient installs cc-sdd separately)
  - **Nothing under `.kiro/`** — `.kiro/` is cc-sdd (kiro) territory and project-specific
    memory. The ccx distribution stays fully independent of it: steering files (project
    policies such as security standards) are authored in the target project via
    `/kiro-steering` / `/kiro-steering-custom`, never shipped by this package.
  If the payload resolves to zero files → **error and stop** (do not produce a
  documentation-only package).
- **Compiled product** (executable/installer produced by a build the developer runs):
  display the placement guidance below and continue; the checklist reports this as a
  manual item.

### Step 2.1 — Documentation set

| File | Source | If missing |
|------|--------|-----------|
| `README.*` | copied from the project-root `README.*` (generated upstream by `ccx-readme-gen`, confirmed present by the deliverable-check step; extension varies — copy whatever extension was found) | error → stop (required deliverable) |
| `THIRD_PARTY_LICENSES.*` | copied from the project-root `THIRD_PARTY_LICENSES.*` (generated upstream by `ccx-thirdlicense-gen`, confirmed present by the deliverable-check step; extension varies — copy whatever extension was found) | error → stop (required deliverable) |
| `CHANGELOG.md` | copy from project-root `CHANGELOG.md` (changelog-gen step) | error → stop (required deliverable) |
| `LICENSE` | copy from project-root `LICENSE` if it exists | warning only → continue (product LICENSE authoring is out of this spec's boundary) |

- Executables / installers are **not** produced by this skill (compiled-product path only). Display a placeholder instruction telling the developer to place the built artifact into the directory:
  ```
  ℹ️  実行ファイル/インストーラーは開発者が Release/{tool-name}-{version}/ に配置してください（本スキルはビルドを実行しません）。
  ```
- Do not run any compiler or build command.

## Step 3: Create the Zip Archive

Use the Bash tool to invoke Windows PowerShell's `Compress-Archive` (no external tools; see research.md):

```
powershell -Command "Compress-Archive -Path 'Release/{tool-name}-{version}/*' -DestinationPath 'Release/{tool-name}-{version}.zip' -Force"
```

- The `/*` on `-Path` packs the directory contents; `-Force` overwrites an existing archive (re-run scenario).
- Before archiving, verify the required deliverables exist in the directory: the
  **distribution payload** (file-based product path — its absence is an error, not a
  warning), README.*, THIRD_PARTY_LICENSES.*, CHANGELOG.md. `LICENSE` absence is a
  warning, not a stop.

## Step 4: Distribution Checklist Report

Confirm each item of the Build and Distribution Checklist from `.kiro/steering/distribution.md` and report the result:

| Checklist item | How to confirm |
|----------------|----------------|
| Distribution payload included | Step 2.0 copied the product files (file-based), or developer placement guidance was shown (compiled) |
| Version number updated | version-management step wrote the root VERSION file (and manifest.json) |
| CHANGELOG.md updated | changelog-gen step produced a new entry |
| README up to date | deliverable-check step confirmed `README.*` exists (generated by `ccx-readme-gen`) |
| THIRD_PARTY_LICENSES updated | deliverable-check step confirmed `THIRD_PARTY_LICENSES.*` exists (generated by `ccx-thirdlicense-gen`) |
| Security Gate 3 passed | prerequisite check confirmed security-report-review.md GO |
| Build artifacts verified in clean env | manual — mark as developer responsibility |
| Checksums generated | optional — guidance only |

Render the report as a table with ✅ / ⚠️ / ❌ per item.

- If any **mandatory** item (payload for a file-based product, version, CHANGELOG, README, THIRD_PARTY_LICENSES, Gate 3) is not satisfied, mark it ❌ and warn:
  ```
  ⚠️  配布非推奨: 必須チェック項目に未達成があります（{items}）。配布前に解消してください。
  ```
- Items that are inherently manual (clean-env verification, checksums) are reported as ⚠️ guidance, not failures.

## Output of This Step

The final report includes the archive path (`Release/{tool-name}-{version}.zip`), the checklist table, and the overall verdict (distribution-ready / not recommended). This is the terminal step of the pipeline.
