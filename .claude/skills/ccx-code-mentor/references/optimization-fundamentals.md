## 1. メモリ階層とキャッシュ

### 教え方の比喩

- **L1キャッシュ = 作業机の上**(手を伸ばせば届く。約1ns、32〜64KB程度)
- **L2キャッシュ = 机の引き出し**(約3〜5ns、256KB〜1MB程度)
- **L3キャッシュ = 部屋の本棚**(約10〜20ns、数MB〜数十MB)
- **メインメモリ(RAM) = 図書館**(約60〜100ns。L1の約100倍遅い)

CPUは計算そのものより「データが届くのを待つ時間」で遅くなることが多い、というのが現代の最適化の出発点。

### キャッシュラインという単位

メモリは1バイトずつではなく **キャッシュライン(通常64バイト)単位** で運ばれる。つまり配列の要素を1つ読むと、隣の要素も「ついでに」机の上に載る。

ここから導かれる実践則:

- **連続したメモリを順番に読むコードは速い**(次のデータが常に机の上にある。ハードウェアプリフェッチも効く)
- **飛び飛びに読むコードは遅い**(毎回図書館まで往復する)
- 配列(連続)はリンクリスト(飛び飛び)より走査が速い理由がこれ
- 2次元配列は**行方向(メモリ順)にループを回す**。行/列の順を間違えるだけで数倍遅くなることがある

```c
// 良い例: メモリ順(行→列)に読む
for (int i = 0; i < N; i++)
    for (int j = 0; j < M; j++)
        sum += a[i][j];   // a[i][j] と a[i][j+1] は隣接 → キャッシュに乗る

// 悪い例: 列→行で読むと、毎回 M*4 バイト先へジャンプ
for (int j = 0; j < M; j++)
    for (int i = 0; i < N; i++)
        sum += a[i][j];   // 大きな配列ではキャッシュミスの連続
```

## 2. データレイアウト(AoS vs SoA)

- **AoS (Array of Structures)**: `struct Enemy { pos; hp; name; }` の配列。オブジェクト指向的で読みやすい。
- **SoA (Structure of Arrays)**: `posの配列`、`hpの配列` を別々に持つ。

毎フレーム「全敵の pos だけ」を処理するなら、SoA は必要なデータだけがキャッシュラインに詰まって届くので速い。AoS だと使わない hp や name まで机の上に運ばれ、キャッシュを無駄遣いする。

教えるときは「処理の単位がオブジェクトごとなら AoS、同じフィールドの一括処理なら SoA」という判断基準まで伝える。SoA は可読性が下がるので、ホットパス限定のテクニックであることも添える。

## 3. SIMDと自動ベクトル化

**SIMD (Single Instruction, Multiple Data)**: CPUの1命令で4〜16個のデータを同時に計算する仕組み(SSE=128bit、AVX2=256bit、AVX-512=512bit。float なら 4/8/16個ずつ)。

現代のコンパイラは、条件が揃った単純なループを**自動的に**SIMD命令へ変換する(自動ベクトル化)。プログラマの仕事は「コンパイラがベクトル化しやすい形」でループを書くこと。

### ベクトル化されやすいループの条件

1. **ループ回数がループ開始前に確定している**(途中の `break` や早期 `return` がない)
2. **ループ内に分岐(if)が少ない**。あっても三項演算子や `max/min` に置き換えられる形
3. **反復間に依存がない**(`a[i] = a[i-1] + x` のような前の結果を使う形はベクトル化できない)
4. **メモリアクセスが連続**(`a[i]` は良い、`a[index[i]]` のような間接参照は苦手)
5. **関数呼び出しがループ内にない**(インライン化される小さい関数はOK)
6. C/C++ではポインタの**エイリアス**(同じメモリを指す可能性)があるとコンパイラが安全側に倒してベクトル化を諦める → `restrict` や添字アクセスで解決

```c
// ベクトル化されやすい: 依存なし・分岐なし・連続アクセス
for (int i = 0; i < n; i++)
    out[i] = a[i] * 2.0f + b[i];

// されにくい: 反復間依存(前の結果が必要)
for (int i = 1; i < n; i++)
    a[i] = a[i-1] * 0.5f;

// 分岐をやめて選択にするとベクトル化されやすくなる
for (int i = 0; i < n; i++)
    out[i] = (a[i] > 0) ? a[i] : 0;   // これは「マスク付き選択」に変換できる
```

ベクトル化されたかどうかは推測せず確認する: コンパイラの最適化レポート(GCC/Clang: `-fopt-info-vec` / `-Rpass=loop-vectorize`)や godbolt で確かめる方法を教える(→ c-cpp-rust.md)。

## 4. 分岐予測とコードフェッチ

CPUは命令を数百段のパイプラインで先読み実行しており、if文に出会うと**結果が出る前にどちらに進むか予測して**先の命令を読み始める(分岐予測)。

- **予測が当たる分岐はほぼタダ**(1サイクル未満)
- **予測が外れると先読みした作業を全部捨てる**(約15〜20サイクルの損失)

### 実践則

- **99%一方にしか行かない分岐は安い。** エラーチェックの if は遠慮なく書いてよい — 予測器がすぐ学習する。これを初学者に伝えると「if文は遅いから消す」という誤った最適化を防げる
- **50:50でランダムに分かれる分岐は最悪**(半分外れる)。ソート済みデータだと同じコードが数倍速くなる有名な現象はこれが原因
- 予測不能な分岐は**branchless化**(条件を算術に変える: `max()`、三項演算子、条件付き代入)を検討。ただし可読性が落ちるので計測してから
- **ホットパスの中に滅多に実行されない大きなコード(エラー処理等)を置かない。** 命令もキャッシュ(命令キャッシュ)から読まれるので、よく使うコードが小さくまとまっているほど命令フェッチが速い。稀な処理は関数に切り出すと、ホットループが命令キャッシュに収まりやすくなる
- C++20 `[[likely]]/[[unlikely]]`、GCC/Clang `__builtin_expect` で「この分岐はほぼこちら」とコンパイラに伝え、よく通る側のコードを直線的に配置させられる(→ c-cpp-rust.md)

### 言語による違い(分岐の扱いは言語で答えが変わる)

分岐予測の質問で言語が明示されていない場合、この対比を1〜2行で教えると原理として身につく:

- **C/C++/Rust(事前コンパイル言語)**: コンパイル時に実行データを知らないので、偏りはプログラマが伝える。C++20 `[[likely]]/[[unlikely]]`、C では `__builtin_expect`、Rust では `#[cold]` や `core::intrinsics::likely`(nightly)。またはPGO(プロファイルに基づく最適化)ビルドで実測データを与える
- **C#/.NET・Java(JIT言語)**: 実行時にJITコンパイラが**実際の分岐の偏りを観測して**自動でコード配置を最適化する(.NET の Dynamic PGO、JavaのC2コンパイラ)。**手動の分岐ヒント構文はそもそも存在せず、対応不要**。「JITが勝手にやってくれるので、エラーチェックを気にせず書いてよい」と伝えると初学者は安心する
- どちらの世界でも「予測が当たる分岐は安い」という原理自体は共通

## 5. 計測の作法

最適化の話をするとき、必ず計測方法もセットで教える:

1. **最適化ビルドで測る**(デバッグビルドの計測は無意味。C/C++: `-O2`、Rust: `--release`、C#: Release構成)
2. **ウォームアップしてから測る**(初回はキャッシュが冷えている・JITが走る)
3. **複数回測って中央値を見る**(1回の計測はノイズだらけ)
4. **道具**: ベンチマークは BenchmarkDotNet (C#) / google-benchmark (C++) / criterion (Rust) / timeit (Python)。プロファイラは Unity Profiler、Visual Studio Profiler、perf (Linux)、Superluminal など
5. **マイクロベンチマークの罠**: コンパイラが「結果が使われない計算」を丸ごと消すことがある。結果を必ず使う(表示する・変数に足し込む)こと

## 6. 教えるときの数字早見表

| 操作 | おおよその時間 |
|---|---|
| L1キャッシュ参照 | 約1ns |
| 分岐予測ミス | 約5〜10ns(15〜20サイクル) |
| L2キャッシュ参照 | 約4ns |
| L3キャッシュ参照 | 約10〜20ns |
| メインメモリ参照 | 約60〜100ns |
| SSD ランダム読み | 約100µs(RAMの1000倍) |
| GC(世代0、C#) | 数十µs〜 |
| GC(フルGC、大きなヒープ) | 数ms〜数百ms ← 60FPSの1フレームは16.6ms |

数字は世代により変わるので「桁の感覚」として教える。重要なのは絶対値ではなく**比率**(RAMはL1の約100倍遅い、など)。
